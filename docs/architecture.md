# 从内核执行证据到板级配置

## 要回答的问题

某个选项是否必须在负载前可用？若只在负载期需要，能否先启动再加载？若从未命中，在这块板的使用契约中是否允许关闭？这是三个不同的问题。跟踪器回答时间和来源，板级清单提供授权，Kconfig 决定请求能否成立，最后用相同负载验证行为。

## 组件与契约

| 边界 | 输入 | 输出与责任 |
|---|---|---|
| 板级构建 | 干净内核源码、已求解基线和经审计的组件清单 | 固定本轮编号、生成编译包装器，使内核和探针绑定到同一次构建。 |
| Clang 前端 | 一个被选中的 C 翻译单元、编号和探针声明 | 在普通函数定义入口插入带常量编号的调用，随编译输出插入点数量。 |
| 内核驱动 | 执行中的编号、初始化回调边界和采集命令 | 在内存中去重，冻结后由字符设备输出快照；不采集调用参数、地址、文件内容或进程名称。 |
| 配置处理 | 基线、清单、编译收据和至少一份完整快照 | 以配置项聚合，终端审阅只允许撤回建议，输出请求值、理由和延迟清单。 |
| 构建与回放 | 审阅后的请求和同版本 Kconfig | 对完整配置重新求解，拒绝未授权的连带变化；用不含采集代码的内核和对应模块回放。 |

### 编号与构建身份

编号属于源文件，不是运行时地址。清单将它关联到 Kconfig 选项、模块、策略和源码路径；同选项的多个翻译单元可以共享决策，但不能各说各话。自动发现只接受简单、直接且非条件块中的 Kbuild 规则，输出默认全为 `keep`。复杂聚合、架构条件、头文件和源码内部的配置开关需要人工审计；模块名和配置名不是可以互换的字符串。

编译包装器只处理绝对源码路径精确匹配的目标对象，不拦截主机工具。每次构建使用随机种子，将原始清单和完整基线的字节共同纳入摘要。调用点引用带完整摘要的链接符号；采集内核另有专属发行后缀。验证器将每个待加载模块的发行标识与客体内核逐次核对，不依赖启用符号版本校验时内核可能放宽的版本字符串检查。编译后再次检查目标对象的未定义符号和真实 `KBUILD_MODNAME`。同一模块还有未登记的已编译成员，或已审计目录中存在同选项的其他直接对象时，整个选项保留。遇到已知直接归属冲突、模块名歧义、零插入点或缺失对象，也不接受该文件的负证据。

编译收据记录前端插入的入口数量，不代表优化后保留了同样数量的机器调用点。至少一个调用保留时才接受该对象。即使选项的所有**登记文件**都有收据，也不能证明登记范围涵盖全部功能。汇编、数据表、头文件独立路径、设备固件、DMA 行为和从未测试的异常路径尤其需要额外判断。

### 为什么驱动分成两部分

启动时的内建函数不能依赖稍后才会加载的 `.ko`。因此只在采集版编译 `init/init_task.c` 时附加记录端代码，不复制或改动任何上游源码。它从启动起持有固定大小的数据表，导出探针和控制接口。树外模块通过标准 Kbuild 的 `M` 和 `MO` 编译，注册 `/dev/kconfig-trace`。卸载控制模块也不会让已插桩代码跳到已释放的模块地址。候选内核使用原编译器，不含这两部分。

不采用逐次输出内核日志：这里需要的是组件是否在某阶段出现过，而不是无界事件流。也不在负载结束后按函数地址猜模块；内联、模块卸载和地址随机化均会损害这种归属方式。

## 时间窗口与初始化

每个编号有三个独立命中位：启动位表示开始命令之前的非初始化执行，包括用户空间预热；负载位表示开始和停止之间的非初始化执行；初始化位表示被跟踪的同步初始化调用链。采样面向整台设备，不能解释为某个进程独占的因果轨迹。

1. 静态排除初始化段、退出段、显式内联、特殊调用约定、不可插桩函数等。完整清单见 `plugin/README.md`。
2. 内建驱动通过内核的 `initcall_start` 和 `initcall_finish` 跟踪同步初始化链。按当前任务而非处理器记账，允许回调睡眠、迁移和嵌套。负载窗口内新加载模块所调用的普通辅助函数也只记初始化位。
3. 中断借用被打断任务的上下文时，不直接继承其初始化标记。转交独立工作线程的异步操作也不按初始化排除；宁可保留额外依赖。最早期在跟踪注册之前发生的可见普通调用保守记为启动使用。
4. 负载前写 `start`，等待业务和需计入的异步操作完成后写 `stop`。两条命令均以换行结尾。每次启动只允许一个窗口，重新加载控制模块不会重置它；需要重复实验时重新启动并合并快照。

初始化时运行过，不代表必须内建；初始化没有产生负载命中，也不代表它的注册副作用可省略。根盘、控制台、看门狗、恢复、升级、安全策略及设备必需的注册，即使只有初始化位也应保持 `keep`，直到有独立的替代依据。

### 并发与开销

编号直接索引原子状态字，每项占一个 `atomic_t`。初始化跟踪使用固定桶和有界槽；只有进入或退出初始化时修改任务表，普通探针不分配、不睡眠、不写日志。重复命中已设置的同阶段位不再写共享缓存行；第一次通过比较交换置位。跟踪器溢出或初始化钩子未就绪会拒绝采集，而不是交出看似完整的空表。

开始和停止命令串行执行，逐编号推进阶段，时间与登记文件数成正比。热路径观察到阶段变化会重新判定，旧写入不能穿过该编号的冻结边界。命令执行期间不是全机统一时刻；负载必须在开始命令返回后启动，在停止之前完成。冻结后快照可多次读取且无须暂停处理器。这里只说明成本结构，没有将虚拟机吞吐量外推到开发板。

## 决策与发布边界

同一构建的多个窗口按位取并集，同一选项的所有文件再次取并集。默认保留所有未映射项。已启用项只有在覆盖完整且没有启动命中时才进入下一步：`drop` 还要求没有负载命中；`defer` 需要明确模块名且模块支持内建，即使负载命中过也可建议 `m`。`init` 只作解释，不单独触发删减。输入摘要不符、缺行、重复编号、截断等属于错误，不生成方案。

`requested.config` 和 `changes.tsv` 是请求而非最终事实。候选构建验证身份、原值、策略和收据，对照逐项变更重新运行上游 `olddefconfig`。`depends on`、`select`、`imply`、架构或选项类型造成的非预期差异都会阻止发布最终 `.config`。不要把失败目录中的中间配置当成交付物。只有构建成功并找到延迟模块及其声明的硬依赖后，才在候选目录顶层写出最终配置。

配置值 `m` 只表示可以加载；实际发生的时刻属于启动系统。参考验证器在系统就绪之后显式插入模块，在相同业务负载上验证结果，并故意省略模块做反向对照。实板还须检查固件、模组别名、早期用户空间、软依赖和恢复流程。
